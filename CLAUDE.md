# Проект: сервис точного подбора для создания семьи (Казахстан)

## Суть
Пользователь один раз заполняет анкету (≈15 минут) и получает 3–5 проверенных кандидатов в неделю.
Подбор взаимный: кандидат показывается, только если подходит пользователю И пользователь подходит кандидату.
Контакты открываются только при взаимном «интересно». Цель — быстро довести пару до встречи, а не удерживать в ленте.

## Этапы
1. **Сейчас: Telegram-бот (MVP)** — анкета, автоматический расчёт совпадений, ручная проверка подбора админом,
   отправка кандидатов, взаимный интерес, отзыв после встречи. Город запуска: Астана.
2. Позже: мобильное приложение (Expo / React Native) на том же бэкенде и той же базе.
   Поэтому бот — только один из клиентов: вся логика живёт в `core/`, бот её лишь вызывает.

## Стек
- Python 3.12, aiogram 3 (бот), FastAPI (API и админка, этап 1 — минимально)
- PostgreSQL, SQLAlchemy 2 + Alembic (миграции обязательны, никаких ручных правок схемы)
- pytest для тестов
- Конфигурация через `.env` (токен бота, строка подключения к БД). `.env` никогда не коммитится.
- Хостинг и база — только на серверах в Казахстане (требование закона о персональных данных).

## Структура
```
core/        # модели, подбор, бизнес-логика (без зависимостей от Telegram)
  models.py
  questions.py   # анкета: вопросы, варианты, слой
  matching.py    # расчёт совпадений — чистые функции, покрыты тестами
bot/         # aiogram: хендлеры, клавиатуры, состояния анкеты (FSM)
admin/       # FastAPI: просмотр анкет, модерация, ручное подтверждение подборки
migrations/  # Alembic
tests/
```

## Модель данных (минимум)
- `users`: id, tg_id, имя, пол, дата рождения, город, готовность к переезду, статус (new / verified / blocked),
  язык интерфейса (kz / ru), дата согласия на обработку данных и версия текста согласия
- `photos`: user_id, file_id, is_selfie_check
- `questions`: id, layer (filter / values / lifestyle), text_ru, text_kz, options (JSON)
- `answers`: user_id, question_id, own_option, acceptable_options (массив), importance (0 / 1 / 2)
- `matches`: user_a, user_b, score, week, status_a, status_b (pending / interested / declined), created_at
- `feedback`: match_id, from_user, met (bool), liked (bool), reason (текст)
- `reports`: from_user, on_user, reason, resolved

## Анкета: три слоя
1. Фильтры (жёсткие): возраст, город/переезд, курение, алкоголь, работа, был(а) в браке, есть дети.
2. Семейные ценности: религиозность, роль и одобрение родителей, жить отдельно или с родителями,
   работает ли жена после брака, сколько детей, язык в семье, традиции (той, қалыңмал).
3. Образ жизни: деньги, быт, отдых, ритм дня, решение конфликтов.
Каждый вопрос: свой ответ + приемлемые ответы партнёра + важность.

## Алгоритм подбора (core/matching.py)
1. Отсечь пары, не проходящие жёсткие фильтры ОБЕИХ сторон, и заблокированных.
2. Веса важности: неважно = 0, важно = 10, очень важно = 50.
3. S(A→B) = сумма весов A по вопросам, где ответ B входит в приемлемые для A / сумма весов A.
4. Итог = sqrt(S(A→B) × S(B→A)). Пары с итогом ниже порога (старт: 0.6) не показываются.
5. Не повторять кандидатов, которых пользователь уже видел.
6. Для каждой пары формировать объяснение: какие важные пункты совпали, где расхождения.
7. Опция «жеті ата» — добровольная: пользователь может попросить исключить кандидатов своего ру.
   Ру хранится только для этой проверки, нигде не показывается, не используется как фильтр поиска.

## Правила разработки
- Владелец проекта не программист: объяснять решения и ошибки простыми словами, без лишних терминов.
- Работать маленькими шагами: одна функция или один экран за раз, после каждого шага — тесты и коммит.
- Перед крупной задачей сначала предложить план и дождаться подтверждения.
- Все тексты для пользователя — в отдельном файле локализации (ru и kz), не хардкодить в хендлерах.
- Персональные данные: собирать минимум, не логировать анкеты и фото, доступ админа только через админку.
- Не добавлять фильтров по национальности. Никаких платёжных функций до отдельного решения.
- Тесты для matching.py обязательны: взаимность, фильтры, веса, пограничные случаи (нет ответов, все «неважно»).
